# 2026-10-09

## 腾讯云 CI/CD 发布体系搭建

分析项目架构后落地「轻量服务器 + docker compose + TCR + tag 触发自动部署」方案。

### 新增文件
- `docker-compose.prod.yml` — 生产编排：单容器、数据卷、日志轮转(20m×5)、`CNDB_DATA_DIR=/data`
- `deploy/Dockerfile.prod` — 生产镜像：预建 `/data` 并 chown 给非 root、内置 HEALTHCHECK、装中文字体
- `deploy/deploy.sh` — 服务器端部署：预备份 → pull → 重建 → 轮询 `/api/health` → 失败自动回滚
- `deploy/backup.sh` — 定时备份（校验非空、可选 COS 上传、按天清理）
- `deploy/.env.prod.example` — 环境变量模板
- `.github/workflows/deploy-tencent.yml` — tag 触发的 build + deploy 两 job
- `docs/DEPLOY_TENCENT.md` — 完整部署文档

### 顺带修复的既有缺陷（重要）
1. **`docker-compose.wheel.yml` 健康检查打 `/health`，该端点不存在**（代码只有 `/api/health`）
   → 容器永远 unhealthy，`depends_on: service_healthy` 死锁，web 容器无法启动。已修正。
2. **compose 只设 `CNDATABASE_URL` 而未设 `CNDB_DATA_DIR`**
   → `UPLOAD_DIR`/`BACKUP_DIR` 等仍派生自 `~/.cndb` 留在容器可写层，
   **容器重建后用户上传的附件全部丢失**。已在三个 compose 中统一补 `CNDB_DATA_DIR=/data`。
3. **healthcheck `start_period` 10s 过短** → 首次启动跑 alembic 迁移会被误判失败，改 60s。
4. **`.gitignore` 的 `.env.*` 误伤 `deploy/.env.prod.example`** → 补 `!` 例外，否则 CI 拿不到模板。

### 踩坑要点（下次直接用）
- **TCR 服务账号用户名必须把 `tcr$` 改成 `tcr@`**，官方明确说明部分 CI 平台无法正确处理 `$`。
- **`CORS_ORIGINS` 必须是 JSON 数组字符串**（`["https://a.com"]`）。它是 `list[str]` 类型，
  pydantic-settings 对复杂类型环境变量按 JSON 解析，写成逗号分隔会抛 `SettingsError` 导致容器启动即崩。
- **SQLite 备份不能用 `cp`**，必须用项目自带的 `cndb backup`（走 native 备份 API，避免快照撕裂）。
- **cndb 没有 `cndb migrate` 子命令** —— schema 迁移在 FastAPI lifespan 启动时自动执行。
- `restore` 用位置参数 `archive` + `--force`，支持 `--dry-run` 预检。
- `sed -i` 改 `.env` 会遗留 `.env.bak` 且非原子，已改为 `mktemp` + `mv`。

### 项目架构备忘
- FastAPI + SQLAlchemy Core + 插件化（accounts/workspaces/tables/reports/wechat_auth），运行时动态建表
- 前端 Vite → `src/cndb/static/` → 打进 wheel（pyproject `force-include`）
- wheel 版单容器形态最适合云部署；源码版双容器带 nginx 是给需要 gzip/SSL 的场景
- 数据路径：一切可写数据派生自 `DATA_DIR`（默认 `~/.cndb`），`CNDB_DATA_DIR` 可整体覆盖

## BUG 与冗余配置清理（门禁全绿前提下）

静态检查（ruff/pyrefly）与测试本就全绿，问题集中在**配置与部署链路**——代码没问题，配置在说谎。

### 修复的真实BUG

1. **`CNDATABASE_URL` 被静默忽略（最隐蔽，优先级最高）**
   - 根因：pydantic-settings 按字段名读环境变量，`Settings.DATABASE_URL` 只认 `DATABASE_URL`；
     而 compose / `.env.prod.example` / README / 部署文档**统一写 `CNDATABASE_URL`**。
   - 后果：容器正常启动、无任何报错，但**永远连 SQLite**。切PostgreSQL 的用户会以为配好了。
   - 修复：`Settings.DATABASE_URL` 加 `validation_alias=AliasChoices("DATABASE_URL", "CNDATABASE_URL")`。
     选alias 而非改文档——文档/部署脚本散布在5 处，代码一处改动成本最低且向后兼容。
   - 回归：`tests/test_config.py` 补 3 个测试（双变量名 + 默认回落）。
2. **根 `Dockerfile:44` `COPY ... tox.ini` 指向已删文件** → `docker build` 必失败。
   改为 `COPY pyproject.toml uv.lock README.md ./`（原漏拷 uv.lock，`--frozen` 会失效）。
3. **`deploy/Dockerfile` 阶段1 用 `npm install` + `package-lock.json`**，但仓库唯一锁文件是
   `pnpm-lock.yaml`，且 `package-lock.json` 不存在 → 阶段1 失败。改为 corepack + pnpm。
4. **`docker-compose.yml` 的 `web.context: ..`** → 构建上下文变成仓库**父目录**，
   找不到 `frontend/`。改为 `context: .`。
5. **`.dockerignore` 写了行尾注释**（`dist/*.tar.gz   # 仅排除...`）→ Docker 不支持行尾注释，
   整行被当pattern，**sdist 从未被排除**。同时补`frontend/node_modules`（501MB）等排除，
   构建上下文从 ~700MB 降到 ~10MB。
6. **`CNDATABASE_URL_PG` 是死配置**——全仓库无任何代码读取，已删除。

### 冗余配置清理
- `frontend/package.json` 补`"packageManager": "pnpm@12.4.2"`：原先CI/本地/Docker
  三处各猜各的 pnpm 版本；corepack 依赖此字段才能锁定。
- 三个 compose + README 的 `--profile pg` 说明修正：**profile 只拉起 postgres 容器，
  app 仍读 CNDATABASE_URL**，必须同时显式指向 pg，否则 pg 容器空转。

### 方法论沉淀
> ruff/pyrefly/pytest 全绿 **≠** 配置正确。本次全部问题都是"配置项存在但不被消费"。
> 审计配置层应交叉验证三件事：① 该环境变量名代码是否真的读；② COPY/依赖的文件是否存在；
> ③ 声明的 profile/开关是否真能改变运行时行为。
