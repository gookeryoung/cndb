## 腾讯云 CI/CD 发布体系搭建

分析项目架构后落地「轻量服务器 + docker compose + TCR + tag 触发自动部署」方案。

### 新增文件
- `docker-compose.prod.yml` — 生产编排：单容器、数据卷、日志轮转(20m×5)、`CNDB_DATA_DIR=/data`
- `deploy/Dockerfile.prod` — 生产镜像：预建 `/data` 并 chown 给非 root、内置 HEALTHCHECK、装中文字体
- `deploy/deploy.sh` — 服务器端部署：预备份 → pull → 重建 → 轮询 `/api/health` → 失败自动回滚
- `deploy/backup.sh` — 定时备份（校验非空、可选 COS 上传、按天清理）
- `deploy/.env.prod.example` — 环境变量模板
- `.github/workflows/deploy-tencent.yml` — tag 触发的 build + deploy 两 job
- `docs/DEPLOY_TENCENT.md` — 完整部署文档

### 顺带修复的既有缺陷（重要）
1. **`docker-compose.wheel.yml` 健康检查打 `/health`，该端点不存在**（代码只有 `/api/health`）
   → 容器永远 unhealthy，`depends_on: service_healthy` 死锁，web 容器无法启动。已修正。
2. **compose 只设 `CNDATABASE_URL` 而未设 `CNDB_DATA_DIR`**
   → `UPLOAD_DIR`/`BACKUP_DIR` 等仍派生自 `~/.cndb` 留在容器可写层，
   **容器重建后用户上传的附件全部丢失**。已在三个 compose 中统一补 `CNDB_DATA_DIR=/data`。
3. **healthcheck `start_period` 10s 过短** → 首次启动跑 alembic 迁移会被误判失败，改 60s。
4. **`.gitignore` 的 `.env.*` 误伤 `deploy/.env.prod.example`** → 补 `!` 例外，否则 CI 拿不到模板。

### 踩坑要点（下次直接用）
- **TCR 服务账号用户名必须把 `tcr$` 改成 `tcr@`**，官方明确说明部分 CI 平台无法正确处理 `$`。
- **`CORS_ORIGINS` 必须是 JSON 数组字符串**（`["https://a.com"]`）。它是 `list[str]` 类型，
  pydantic-settings 对复杂类型环境变量按 JSON 解析，写成逗号分隔会抛 `SettingsError` 导致容器启动即崩。
- **SQLite 备份不能用 `cp`**，必须用项目自带的 `cndb backup`（走 native 备份 API，避免快照撕裂）。
- **cndb 没有 `cndb migrate` 子命令** —— schema 迁移在 FastAPI lifespan 启动时自动执行。
- `restore` 用位置参数 `archive` + `--force`，支持 `--dry-run` 预检。
- `sed -i` 改 `.env` 会遗留 `.env.bak` 且非原子，已改为 `mktemp` + `mv`。

### 项目架构备忘
- FastAPI + SQLAlchemy Core + 插件化（accounts/workspaces/tables/reports/wechat_auth），运行时动态建表
- 前端 Vite → `src/cndb/static/` → 打进 wheel（pyproject `force-include`）
- wheel 版单容器形态最适合云部署；源码版双容器带 nginx 是给需要 gzip/SSL 的场景
- 数据路径：一切可写数据派生自 `DATA_DIR`（默认 `~/.cndb`），`CNDB_DATA_DIR` 可整体覆盖

## BUG 与冗余配置清理（门禁全绿前提下）

静态检查（ruff/pyrefly）与测试本就全绿，问题集中在**配置与部署链路**——代码没问题，配置在说谎。

### 修复的真实BUG

1. **`CNDATABASE_URL` 被静默忽略（最隐蔽，优先级最高）**
   - 根因：pydantic-settings 按字段名读环境变量，`Settings.DATABASE_URL` 只认 `DATABASE_URL`；
     而 compose / `.env.prod.example` / README / 部署文档**统一写 `CNDATABASE_URL`**。
   - 后果：容器正常启动、无任何报错，但**永远连 SQLite**。切PostgreSQL 的用户会以为配好了。
   - 修复：`Settings.DATABASE_URL` 加 `validation_alias=AliasChoices("DATABASE_URL", "CNDATABASE_URL")`。
     选alias 而非改文档——文档/部署脚本散布在5 处，代码一处改动成本最低且向后兼容。
   - 回归：`tests/test_config.py` 补 3 个测试（双变量名 + 默认回落）。
2. **根 `Dockerfile:44` `COPY ... tox.ini` 指向已删文件** → `docker build` 必失败。
   改为 `COPY pyproject.toml uv.lock README.md ./`（原漏拷 uv.lock，`--frozen` 会失效）。
3. **`deploy/Dockerfile` 阶段1 用 `npm install` + `package-lock.json`**，但仓库唯一锁文件是
   `pnpm-lock.yaml`，且 `package-lock.json` 不存在 → 阶段1 失败。改为 corepack + pnpm。
4. **`docker-compose.yml` 的 `web.context: ..`** → 构建上下文变成仓库**父目录**，
   找不到 `frontend/`。改为 `context: .`。
5. **`.dockerignore` 写了行尾注释**（`dist/*.tar.gz   # 仅排除...`）→ Docker 不支持行尾注释，
   整行被当pattern，**sdist 从未被排除**。同时补`frontend/node_modules`（501MB）等排除，
   构建上下文从 ~700MB 降到 ~10MB。
6. **`CNDATABASE_URL_PG` 是死配置**——全仓库无任何代码读取，已删除。

### 冗余配置清理
- `frontend/package.json` 补`"packageManager": "pnpm@12.4.2"`：原先CI/本地/Docker
  三处各猜各的 pnpm 版本；corepack 依赖此字段才能锁定。
- 三个 compose + README 的 `--profile pg` 说明修正：**profile 只拉起 postgres 容器，
  app 仍读 CNDATABASE_URL**，必须同时显式指向 pg，否则 pg 容器空转。

### 方法论沉淀
> ruff/pyrefly/pytest 全绿 **≠** 配置正确。本次全部问题都是"配置项存在但不被消费"。
> 审计配置层应交叉验证三件事：① 该环境变量名代码是否真的读；② COPY/依赖的文件是否存在；
> ③ 声明的 profile/开关是否真能改变运行时行为。

## 迁移到 CNB 云原生构建（.cnb.yml）

### 新增文件
- `.cnb.yml` — CNB 流水线，四档触发
- `.cnb/Dockerfile.ci` — CI 基础镜像（node22 + python3.12/uv + pnpm12.4.2 + docker CLI + 中文字体）

### 触发矩阵与规格（机时≈ cpus × 容器存活时长）
| 触发 | 内容 | cpus |
|---|---|---|
| `$.pull_request` | gitkeep + ruff + pyrefly + 前端 typecheck/lint/test | 2 |
| `main.push` | 快速门禁 + pytest 覆盖率(95%, -n4) + 前端 build + bundle:budget | 4 |
| `v*.*.*.tag_push` | 前端 build → wheel → 镜像推 TCR+CNB制品库 → 冒烟 → SSH 部署 | 2 |
| `$.api_trigger_e2e` | Playwright 全量 E2E（手动触发） | 4 |

### 省机时的四个决策（成本优化的核心）
1. **降配**：lint/pyrefly/tsc 单线程密集，2 核足够；只有 pytest 覆盖率吃满 4 核。
   E2E 从 GitHub 的 4 分片×`continue-on-error` 降为**手动触发单容器不分片**（分片要重复装 chromium，更贵）。
2. **合并容器**：装依赖与检查放同一容器，避免为装依赖单独付容器启动成本。
   前后端门禁**串行**而非并行——串行失败即中断，避免"前端白跑 5 分钟才发现后端挂了"。
3. **缓存**：`docker.volumes` 的 `copy-on-write` 缓存 uv / pnpm store / ms-playwright / docker buildx，
   依赖安装从 ~90s 降到 ~10s。镜像层缓存用 buildx `--cache-from/--cache-to type=registry`。
4. **降频**：tag 流水线**不跑测试**（main 全量门禁通过后才打 tag，重复跑纯浪费）。

### CNB 语法踩坑（重要）
- **`$` 兜底分支块下不能出现两次顶层 `$:` 键**——YAML 同名键后者覆盖前者，
  会让 `pull_request` 整块静默消失。`pull_request` 与 `api_trigger_e2e` 必须写在同一个 `$` 下。
- `runner.cpus` 内存 = cpus × 2GB。
- 凭证走 `imports: https://cnb.cool/<slug>/<secrets-repo>/-/raw/main/deploy-env.yml`，
  密钥仓库需为公开可读 raw；本文档凭证变量：TCR_REGISTRY/TCR_GROUP/TCR_USERNAME/TCR_PASSWORD/
  SSH_HOST/SSH_PORT/SSH_USERNAME/SSH_PRIVATE_KEY。
- 内置镜像仓库 tag：`${CNB_DOCKER_REGISTRY}/${CNB_REPO_SLUG_LOWERCASE}/...`，无需 docker login。
- 旧 buildx 导 cache 报 404 → `--cache-to` 加 `image-manifest=true,oci-mediatypes=true`。
- `--platform linux/amd64` 显式指定：host 是 arm64 时 wheel 里 `src/` 纯 Python 无碍，
  但 node 依赖需按目标架构装。
- `set -e` 不跨 `|`管道/命令替换传播，脚本里靠 `||`/`&&` 链式兜。
- **CNB 派发到 3 个构建节点**，节点本地缓存命中率约 1/3；要跨节点稳定复用必须走 docker:cache 镜像。

### 推送后首次真实构建暴露的3 个缺陷（已修，提交 ee81c4e）

CNB 的 `docker.build` 会**真正构建 Dockerfile**，不像 GitHub Actions 那样容错。
前两次构建均在 8~15 秒内挂在同一层（`RUN apt-get install`），第三次才通过。
**教训：Dockerfile 类改动无法靠 YAML 校验发现问题，本地无 Docker 时更要先读日志。**

1. **GNU sed 没有 `-o` 选项**（那是 rsync 的）。
   第一次想用 `sed -i -o` 让缺失文件静默跳过，实际导致 sed 打印 help 并 exit 1。
   正确做法：`for f in ...; do [ -f "$f" ] && sed -i ... "$f"; done`。
   注意 sed 是**单命令**，`[ -f ] && sed` 在循环里没问题，但 `A && B || C` 链式在shell 里
   有优先级陷阱，别混用。
2. **Debian bookworm 起 apt 源是 deb822 格式**：
   `/etc/apt/sources.list.d/debian.sources`，不再有 `/etc/apt/sources.list`。
   仓库里 `deploy/Dockerfile.prod` 早就处理过这个差异（改 `.d/debian.sources`），
   我写新文件时沿用了旧写法 —— **同一仓库内的 Dockerfile 应共享镜像源替换逻辑**。
3. **`node:22-bookworm-slim` 不含任何 Python**，必须 `uv python install 3.12`
   （项目 requires-python >=3.12，bookworm apt 只有 3.11）。
4. **`apt-get install docker.io` 是陷阱**：会连带装完整 daemon（~250MB），
   且与 `.cnb.yml` 里 `services: [docker]` 提供的外部 daemon 冲突。
   只需CLI 时用官方静态二进制 `download.docker.com/linux/static/stable/<arch>/docker-<ver>.tgz`，
   buildx 插件另下 GitHub release 放到 `/root/.docker/cli-plugins/docker-buildx`。

### CNB 运行时观察
- **`runner.cpus` 生效且可见**：构建记录里 `ARCH=amd64,cpus=4,memory=8`，
  内存自动为 `cpus × 2GB`。日志 `labels` 字段可验证规格是否按预期生效。
- **同一提交可能触发多条流水线**：`event: issue.comment@npc` 是 CNB 的 NPC AI 助手
  自动触发的（cpus=8），**不在 `.cnb.yml` 配置范围内**，纯白烧机时。
  → 需在仓库网页端关闭 NPC/AI 助手，否则每次提交会多跑一条 8 核流水线。
- **`cnb.build.get-build-logs --repo <slug>`** 查构建列表；
  `cnb build build-runner-download-log --repo <slug> --pipelineId <id>-001`
  下载 runner 日志（返回本地临时文件路径，需用 Read/Grep 分析）。
- 状态机：`prepare`（排队等资源，不计费）→ `pending`（运行中）→ `success`/`error`。

   `/etc/docker/daemon.json` 配 `mirror.ccs.tencentyun.com`（腾讯云内网源，返回 200）；
   git clone 走 `https://ghfast.top/https://github.com/...` 代理。

**2核2G 机器本地构建镜像的实测代价**（这是决定走 TCR 的依据）：
首次构建耗时 ~25 分钟，磁盘 +2.2G（frontend/node_modules 452M + Node18/Python3.12/gcc
工具链常驻）。构建期CPU/内存打满，有 OOM 连带杀掉线上容器的风险。结论：后续发版应走
TCR + GitHub Actions，服务器只做 pull，不要在服务器编译。

**发现的项目 bug（未修，待议）**：`src/cndb/core/config.py` 的 `STATIC_DIR = BASE_DIR / "static"`
在 wheel 安装模式下解析错误 —— `_find_project_root()` 兜底返回 `site-packages`，导致
STATIC_DIR 指向 `site-packages/static`（不存在），真实文件在 `site-packages/cndb/static`。
不影响运行，因为 `app.py` 用自己的 `_STATIC = Path(__file__).parent / "static"`。
但 CI 冒烟检查断言的正是 `STATIC_DIR.is_dir()`，说明该断言在 wheel 场景下是假通过。

**踩坑**：nginx 1.24 不支持独立的 `http2 on;` 指令，必须用 `listen 443 ssl http2;`，
否则 `nginx -t` 报 unknown directive 并导致 reload 失败。

## STATIC_DIR bug 已修复并提交（e941742）

`src/cndb/core/config.py` 的 `STATIC_DIR` 从 `BASE_DIR / "static"` 改为
`_PACKAGE_DIR / "static"`（新增 `_PACKAGE_DIR = Path(__file__).parent.parent`）。

**为什么开发环境永远测不出来**：开发模式下 `BASE_DIR` = 项目根、
`_PACKAGE_DIR` = `src/cndb`，两者拼出的 static 都在 `src/cndb/static`，
结果完全一致。只有 `uv build` 产 wheel 并安装后，`_find_project_root()`
找不到 pyproject.toml/alembic.ini 兜底返回 site-packages，差异才显现。

**复现与验证方法**（这个套路以后修打包类问题可直接复用）：
```
uv build --wheel --out-dir /tmp/wheeltest
uv venv /tmp/wheelvenv --python 3.12
uv pip install --python /tmp/wheelvenv/Scripts/python.exe <wheel>
/tmp/wheelvenv/Scripts/python.exe -c "from cndb.core.config import STATIC_DIR, BASE_DIR; print(BASE_DIR, STATIC_DIR)"
```
断言 `BASE_DIR.name == "site-packages"` 可确认已触发 bug 的前置条件。

补了两个回归测试（tests/test_config.py）：父目录名必须是 `cndb`；
`STATIC_DIR` 必须与 `app.py` 的 `_STATIC` 同路径。旧代码下两者均失败。
全量 2878 passed / 2 skipped，ruff format + check 通过，pyrefly 0 error。

**遗留建议**：TCR + GitHub Actions 发版通道尚未接通（服务器仍在本地构建镜像）。
