# ADR 0001: 数据表写操作采用表级变更单审批模式

Status: Superseded
Date: 2026-10-12

> 状态说明（2026-10-14 复核）：本 ADR 描述的「扩展 ApprovalInstance 承载变更单」方案已被取代。
> 2026-10-13 的提交 `d8ce450` 移除了表单 / 审批流插件，改为 `plugins/change_requests`
> 表级变更申请（op + 行增量 + 基准快照、字段级漂移检测，见 CONTEXT.md「修改申请」）；
> `ApprovalInstance` 现已不存在于源码，仅历史迁移注释中还有残留。保留本 ADR 仅为记录决策演进。

## Context

数据网格存在三条并行编辑入口（单元格双击速编、行双击 Drawer、操作列整行编辑），写路径直连 `POST/PATCH/DELETE /records`，仅校验表级 `EDIT_RECORDS` 权限后直接落库。现有审批流（ApprovalInstance）只覆盖"表单新增"一条进表通道，表单编辑与网格三入口全部绕过审批，治理上存在多条旁路；三入口之间的权限/锁定门控也不一致。

## Decision

引入表级「编辑需审批」开关（默认关闭）。开启后，该表全部写操作（网格新增/编辑/删除、表单编辑）统一提交为变更单（复用 ApprovalInstance 扩展：op + 行快照/增量），审批通过才由后端落库；审批期间行呈现"原值+行锁定"。三入口保留，做语义分工与门控统一，收敛为同一"提交变更"语义。

## Consequences
- 审批覆盖完整：直编不再构成旁路，三入口交互一致，双击手势歧义消除。
- 写路径分叉（直编 vs 变更单）增加 records/forms 服务层复杂度，需要单点分派与落库失败回退（约束冲突时变更单转失败态，原行数据不变）。
- 已否决的替代方案：门控协同（不堵旁路，审批形同虚设）、乐观显示草稿值（协作者可见未生效数据）、网格纯展示（牺牲编辑效率）。
