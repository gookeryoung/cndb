# 方案与设计文档规范

新功能 / 行为变更必须先出方案，再写代码；**但不是所有需求都写 ADR**，先按复杂度定级，再选方案载体。

## 方案分级（先定性，再选载体）

| 级别 | 判定标准 | 方案载体 |
|---|---|---|
| **S0 小改** | bug 修复、文案 / 样式微调、单点小改动，无数据结构 / 接口 / 权限口径变化，改动面 ≤ 1-2 个模块且方案无分叉 | 无需卡片与 ADR：口头确认意图即可动手，实现后走 L2 门禁链 |
| **S1 常规功能** | 有明确多约束的新功能或行为变更，改动跨 2+ 模块，但设计无架构级分叉 | 需求卡片（可轻量），方案写入卡片「口径」节即可，**不强制 ADR** |
| **S2 重大项** | 满足任一：数据模型 / 迁移 / 备份口径变化；权限 / 安全口径变化；架构选型或模块边界变化；影响图表规范等对外契约；用户明确为重大项；方案存在多个实质分叉需评审 | 需求卡片 + ADR，走完整流程 |

- 拿不准按上一级处理（fail-safe）；用户明确要求写（或不写）ADR 时以用户为准。
- S1 若实现中发现设计分叉或口径开始外溢，升级为 S2 补 ADR，已写的卡片内容直接搬入 ADR。

## 流程（按级别裁剪）

- 需求接入：S1 / S2 把口语需求整理为**需求卡片**（模板 `docs/REQUIREMENT_CARD_TEMPLATE.md`，存 `docs/requirements/NNNN-<topic>.md`），逐句拆成可实施约束并编号 C1..Cn；S0 不需要。
- 方案制定：仅 S2 产出 **ADR** 放到 `docs/adr/NNNN-<topic>.md`（模板 `docs/adr/TEMPLATE.md`，范式参考 `docs/adr/0004-row-level-permission-rules.md`）。
- **结构只以模板为准**：ADR 的章节与字段不在本规则重复列举，改模板即改规范。
- **每类内容只写一次**：需求原文与约束编号 ← 需求卡片；现状核对 / 不变量 / 设计 / 测试 / 分期 ← ADR 正文；决策结论 ← ADR「决策记录」D1..Dn。ADR 引用卡片编号而不复制原文，不另写「已确认决策」清单，Consequences 不重复否决项。
- **需求移除 / 变更时先清理 ADR**：ADR 是首要清理对象 —— 失效的口径行、现状条目、决策 D 行、测试清单与分期一并删除或改写；不保留「历史方案」「以后可能用」段落，整节不适用写「无」。ADR 被新方案替代或需求作废：**直接删除**该 ADR 文件、索引行与全仓引用（git 历史可追溯），不在仓库保留 `Superseded` / `Deprecated` 文档；编号不复用。
- 门禁：ADR 从 `Proposed` → `Accepted` 前，决策记录表不得有「待定」，且卡片约束 C1..Cn 在「口径」表中逐条有落点；新术语写入 `CONTEXT.md`。
- 人工卡点：S1 需求确认（卡片）、S2 的卡片确认与 ADR 评审必须由人拍板，AI 不得自行进入实现；S0 确认意图后可直接实现。
