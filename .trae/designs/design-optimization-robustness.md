# 设计优化与健壮性提升方案

状态：已决策（待用户复核范围取舍）
日期：2026-10-09
来源需求：用户提出"针对项目设计优化和健壮性提升制定方案"

## 1. 决策摘要（ADR）

- **决策问题**：在不改变插件式单体架构、不破坏 Win7 兼容性约束的前提下，如何以最小复杂度提升系统健壮性（错误处理、故障恢复、依赖韧性、可观测性）？
- **决策**：保持单体优先（monolith-first），不做服务拆分；健壮性投入按"错误契约统一 → 外部依赖韧性 → 长任务可靠性 → 可观测性补全"四个阶段推进，每阶段独立可交付、可回滚。
- **状态**：方案已定，实施项以 `[ ]` 标记，完成一项勾一项；全部完成后清理本文档仅保留当前生效设计。

### 备选方案

| 方案 | 结论 | 拒绝理由 |
|------|------|----------|
| A. 维持现状，仅按 bug 驱动修复 | 拒绝 | 错误处理散落（宽泛 except 约 43 处/26 文件），故障模式无统一契约，健壮性靠运气 |
| B. 引入独立任务队列服务（ Celery 类）+ 服务拆分 | 拒绝 | 支付分布式溢价但无对应收益：单机/单容器部署形态（fspack 打包、Windows 服务）下无独立扩缩需求；引入新依赖属暂停条件需用户授权，且破坏轻量分发目标 |
| C. 单体内分层加固（本方案） | 采纳 | 复用现有 plugin/services 分层与任务表模式，每项改动可逆、可测、受 `make check` 门禁保护 |

## 2. 目标与非目标

**目标**：
1. 统一错误契约：服务层异常在路由层完成映射，业务失败返回 400+明细，消除未映射 500。
2. 外部依赖（微信 API、HTTP 导入源）具备显式超时/重试/降级策略。
3. 导入长任务具备幂等恢复与失败可见性（复用现有任务表）。
4. 健康检查升级为就绪探测（探测 DB 可用性），支持部署层探活。
5. 宽泛异常清理：仅允许在边界层（CLI/GUI/顶层）捕获宽泛异常并记录。

**非目标**：
- 不切换数据库默认值（SQLite 仍是默认，PG 仍是可选项）。
- 不升级被 Win7 钉死的依赖版本（pydantic<2.7、bcrypt 3.x、cryptography 41.x）。
- 不引入消息队列、缓存服务等新基础设施。
- 不改前端架构。

## 3. 约束

- Win7 兼容：依赖版本上界不可动（见 pyproject.toml 注释）。
- 门禁：所有改动须通过 `make check`（lint/typecheck/cov≥95/frontend-check）。
- 分层铁律：routers → services → models，路由层禁止 SQL/ORM。
- `.trae/` 不入库；公共 API 变更须同步 schema + 前端类型 + 测试。

## 4. 系统地图与限界上下文

数据流：浏览器/公开表单 → FastAPI(插件路由) → services → SQLAlchemy Session → SQLite(WAL)/PostgreSQL → 文件系统(备份/附件/导入导出)。

| 上下文 | 职责 | 上游 | 下游 | 关系 | 翻译面 |
|--------|------|------|------|------|--------|
| core（config/database/migrations/security） | 引擎、会话、迁移、鉴权原语 | — | 所有插件 | shared kernel | 无 |
| accounts/workspaces | 身份与协作权限 | core | tables | customer/supplier | request.state.user_id |
| tables | 元数据驱动的表格/视图/导入导出/治理 | core, workspaces | 前端、文件系统 | conformist | field_types registry 统一字段模型 |
| reports | 模板渲染（Jinja2） | tables, accounts | 前端/PDF | customer/supplier | 模板上下文字典 |
| wechat_auth | 外部微信登录 | 微信 API（外部） | accounts | anti-corruption layer | client.py 隔离外部协议 |
| frontend | SPA | 全部 REST API | — | conformist | FastAPI 为类型真理源 |

信任边界：公开路由（public_router、公开表单/分享页）与鉴权路由之间；系统管理路由（backup/restore，superuser）；文件上传/下载边界。

## 5. 交互风格决策

导入/导出等长任务维持"任务表 + 轮询"模式（现有 import_tasks），不引入推送/流式：单机部署下轮询足够，复杂度不匹配收益。若未来前端轮询压力成为可测问题，再评估 SSE——列为可逆的两扇门决策。

## 6. 实施项

### 阶段一：错误契约统一（最高优先级）

- [ ] R1.1 盘点全部宽泛 `except Exception`/裸 except（当前 43 处/26 文件），分类为：可保留（边界层+已记日志）与须收敛（吞异常/掩盖根因）
- [ ] R1.2 定义统一异常体系：服务层自定义异常基类 + 错误码，路由层统一 handler 映射为 400/404/409 + 明细，禁止服务层异常裸穿成 500
- [ ] R1.3 `get_db` 增加异常时显式 `rollback()`（当前仅 close，依赖隐式回滚语义），保证嵌套事务场景（见 test_post_commit_nested_txn）行为不变
- [ ] R1.4 为每个收敛点补边界测试（畸形输入、并发锁冲突、磁盘失败模拟）

### 阶段二：外部依赖韧性

- [ ] R2.1 wechat_auth client：显式 connect/read 超时、有限重试（幂等 GET 才重试）、失败降级路径（登录不可用时给出明确错误而非挂起）
- [ ] R2.2 API 导入源（api_fetch）：同上超时/重试策略，失败行导出已有（failed_row_exporter），补"部分成功"语义测试
- [ ] R2.3 外部调用统一走带超时的会话工具，禁止无超时请求散落

### 阶段三：长任务与数据可靠性

- [ ] R3.1 导入任务状态机审计：补齐 任务失败→记录原因→可重试 路径，保证重复触发同一任务幂等
- [ ] R3.2 启动迁移失败面：`ensure_db_migrated` 失败时 CLI/GUI 给出可操作指引（备份恢复/升级提示），而非裸 traceback
- [ ] R3.3 备份恢复健壮性已有测试基础（test_backup_restore_robustness / legacy_compat），补备份文件版本号前向兼容约定（沿用 backup-archive-layout.md）

### 阶段四：可观测性补全

- [ ] R4.1 `/api/health` 升级：区分 liveness（进程存活）与 readiness（DB ping + 迁移版本），供部署探活
- [ ] R4.2 慢查询/外部调用耗时结构化日志（logger，禁止 print），便于本地/单机排障
- [ ] R4.3 关键操作审计覆盖检查（audit 服务已有），补公开路由写操作审计缺口（如存在）

## 7. 适应度函数（架构不变量的可测检查）

| 不变量 | 指标/规则 | 阈值 | 测量源 | 频率 | 失败响应 | 本地路径 |
|--------|-----------|------|--------|------|----------|----------|
| 分层依赖方向 | routers 不得 import models / 禁 SQL | 0 违例 | grep 审计（ruff 自定义规则或 CI 脚本） | 每次提交 | 阻断合并 | `make lint` |
| 错误契约 | 未映射 500（TestClient 断言响应码/明细） | 0 违例 | 边界测试 | 每次提交 | 修复映射 | `uv run pytest tests/test_api_edge_cases.py` |
| 外部调用超时 | 所有外部 HTTP 调用显式 timeout | 0 违例 | 代码审计 + 单测模拟挂起 | 每次提交 | 阻断 | `make test` |
| 覆盖率 | 后端 cov | ≥95 | pytest-cov | 每次提交 | 阻断 | `make check` |
| 前端门禁 | typecheck+lint+test | 全绿 | pnpm | 每次提交 | 阻断 | `make check` |

## 8. 风险登记

| 风险 | 可能性 | 影响 | 缓解 |
|------|--------|------|------|
| 异常收敛改动波及既有测试语义 | 中 | 中 | 每处收敛独立提交；只迁移 patch 路径，不放宽断言 |
| 统一错误码破坏前端契约 | 中 | 高 | FastAPI 为类型真理源，同步前端类型 + API 测试；响应结构做向后兼容（仅新增字段） |
| SQLite 并发锁竞争在收敛后显式化 | 低 | 中 | busy_timeout=5000 + WAL 已就位；补并发写测试 |
| Win7 依赖上界限制修复性升级 | 确定 | 中 | 不动依赖，以应用层韧性（重试/降级）补偿 |
| 迁移失败导致服务无法启动 | 低 | 高 | R3.2 可操作错误面 + 备份恢复路径测试已存在 |

## 9. 运行时依赖责任（设计期采纳标准）

- SQLite（默认）：本地可调试（CLI 查询文件）、可替换（DATABASE_URL）、降级路径（WAL 失败仅告警）、退出路径（迁 PG 仅改 URL+重跑迁移）。维持。
- 微信 API：不可控外部服务——必须有超时/重试/明确失败语义（R2.1），登录失败不阻塞主功能。
- httpx2/requests 并存：长期收敛为单一 HTTP 客户端（低优先，不在本方案范围，仅记录）。

## 10. 可逆性

| 决策 | 可逆性 | 代价 | 重新考虑的触发条件 |
|------|--------|------|-------------------|
| 单体保持 | 两扇门 | 拆分需独立扩缩/发布需求时付出 | 多租户隔离或独立发布节奏成为硬需求 |
| 任务表+轮询 | 两扇门 | 改 SSE/推送约一个视图层改动 | 轮询延迟被用户可感知投诉 |

| readiness 探测 | 两扇门 | 无 | — |
