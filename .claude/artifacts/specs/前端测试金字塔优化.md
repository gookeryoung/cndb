# 前端测试金字塔优化（单元为基、组件为辅、E2E 兜底）- 需求文档

## Overview

- **Summary**：为 `frontend/`（Vite 6 + React 18 + TypeScript + antd 5）建立"单元测试为基石、少量关键路径组件/集成测试、极少数核心流程 E2E"的三层测试体系，并接入提交门禁与 CI，在提升回归覆盖的同时保证测试速度。
- **Purpose**：当前前端测试金字塔倒挂——只有顶层 Playwright E2E（26 用例、需起后端、单条数秒至数十秒），单元/组件测试为零。大量高价值纯逻辑（字段操作符、值格式化、视图 schema、配色、日期、zustand stores、HTTP 拦截器）变更无快速反馈；E2E 还承担了模式按钮矩阵、筛选规则等本应由下层承担的逻辑断言。需要补齐底座、把逻辑断言下沉，让绝大多数回归在秒级暴露。
- **Target Users**：前端开发者（本地秒级反馈）、项目维护者（防回归门禁）、CI（自动化质量闸门）。

## Goals

1. 引入 Vitest 单元测试底座，覆盖核心纯逻辑模块与状态管理。
2. 以 Testing Library + MSW 建设少量（约 4 个关键路径）组件/集成测试，验证真实交互与 API 集成。
3. 将 E2E 中的纯逻辑断言下沉到单元/组件层，E2E 只保留端到端链路并冻结规模膨胀。
4. 单元+组件套件秒级完成，纳入 `make check` 提交门禁；E2E 继续独立于 `make e2e`。
5. 建立覆盖率双门槛：核心逻辑高门槛、全局低水位起步逐轮上调。
6. CI `frontend-check` job 执行单元/组件测试，形成持续观测。

## Non-Goals

- 不追求全部 React 组件 100% 覆盖；展示型、一次性弹窗组件本轮不强制。
- 不替换 Playwright、不重写 E2E 框架，不引入视觉回归测试或跨浏览器测试（E2E 维持仅 chromium）。
- 不对大型组件（GanttView/GridPage 等）做业务重构；仅在测试需要时做小步、行为不变的纯函数抽取。
- 后端 Python 测试、覆盖率（已有 95% 门禁）不在本次范围。
- 不做性能压测、可访问性自动化审计。

4. E2E 策略为**允许下沉精简**：纯逻辑断言下沉后删除 E2E 等价步骤，只保留端到端链路。

## Functional Requirements

- **FR-1 测试基础设施**：可一键运行的 Vitest 体系——jsdom 环境、`@` 别名复用、测试 setup（antd 所需 matchMedia/ResizeObserver 等 polyfill、jest-dom 匹配器、自动 cleanup）、`test`/`test:watch`/`test:coverage` 脚本；测试文件纳入 typecheck 与 ESLint 但不影响生产构建。
- **FR-2 纯逻辑单元测试**：以下模块均有同目录单元测试，覆盖正常/边界/异常路径：
  - grid 领域：`fieldOps`（操作符映射/别名/select options 提取）、`fieldValueFormat`（各类型值格式化）、`dateUtils`、`viewOptionSchema`（schema 解析、字段匹配、默认值回退、自动推断）；
  - 通用：`utils/tagColors`（hash 稳定性/语义推荐/已存颜色优先/缓存）、`hooks/useResponsive`（断点判定与 hook 行为）、`report-editor/jinja2Highlight`（三类 Jinja2 token 识别）；
  - 数据层：`api/client`（token 存取/请求注入/401 重定向/detail 归一化）、`store/auth`、`store/gridView`、`store/tableSettings`（actions、函数式更新、reset、persist 边界）。
- **FR-3 纯函数抽取**：对大组件中明显可分离的纯逻辑（如看板排序与分组键、甘特日期计算、"views 列表→可用视图模式集合"推导）做小步抽取为独立模块并补单测；抽取必须行为不变，不强耦合 UI 的逻辑不硬抽。
- **FR-4 组件/集成测试（关键路径，约 4 个）**：
  1. `ProtectedRoute`：loading / 未登录重定向（含 returnTo）/ 已登录渲染 children；
  2. `GridCell`：按字段类型渲染、行内编辑变更与保存提交；
  3. `ColumnFilterDropdown`：操作符列表随字段类型联动、needValue 处理、应用/重置回调；
  4. 视图配置表单（`CreateEditViewForm` 或 `ViewConfigDialog`）：schema 驱动渲染、必填校验、默认值与自动推断。
  测试通过统一 provider 工具（QueryClientProvider + MemoryRouter + antd 主题）渲染，API 一律经 MSW 模拟，禁止真实网络。
- **FR-5 E2E 下沉精简**：把 FR-2/FR-3/FR-4 已在下层等价覆盖的逻辑断言从 E2E 移除（模式按钮矩阵收敛为代表性 1 例 + 点击切换 1 例；owner 筛选等按相同原则处理）；E2E 只保留"登录→进入表→行增删改→视图切换→导航"端到端链路断言。冻结用例规模：完成后 E2E 用例总数 **≤ 26**，并落地"新逻辑默认单测、仅新核心跨层流程才许加 E2E"的准入约定。
- **FR-6 门禁与 CI**：`make check` 的 frontend-check 串联单元/组件测试与覆盖率门禁；CI `frontend-check` job 增加测试步骤且为强制门禁；E2E job 维持独立（观察期策略本轮不变）。
- **FR-7 测试约定**：明确文件命名与就近放置、AAA 结构、中文用例描述、测试间隔离清理（MSW reset、localStorage 清空、store 重置）、禁真实定时器/真实网络等约定，便于后续遵循。

## Non-Functional Requirements

- **NFR-1 速度**：单元+组件全量套件在典型开发机冷跑 ≤ 15 秒；watch 增量模式秒级反馈；不启动后端、不启动浏览器。CI 中命中缓存时该步骤 ≤ 60 秒。
- **NFR-2 稳定性**：单元/组件测试零 flaky——不使用真实固定等待（`setTimeout` 靠 fake timers 或 RTL 自动等待）、不依赖网络、不依赖宿主机时区外的环境因素；连续重复运行结果一致。
- **NFR-3 覆盖率**：核心逻辑集合（FR-2/FR-3 模块）行/语句覆盖 ≥ 90%、分支 ≥ 85%；全局（全部 `src`）行覆盖 ≥ 30% 作为首版低水位（首跑后按实际值校准为不低于 30% 的 5 的整数倍，防止首日即红），后续迭代只升不降。
- **NFR-4 隔离性**：每个用例后自动完成 DOM cleanup、MSW handler 重置、localStorage/sessionStorage 清空、zustand store 状态重置；用例间无共享可变状态。
- **NFR-5 兼容性**：与 pnpm + Vite 6 + TS 5.6 strict + ESLint 9 flat config 共存；新增配置/依赖不破坏 `pnpm build`（产物同步 `src/cndb/static` 的既有行为不变）、不破坏后端打包。

## Constraints

- **技术**：antd 5 在 jsdom 下需 polyfill（matchMedia、ResizeObserver、getBoundingClientRect、scrollTo 等）；zustand persist 依赖 localStorage；axios 与 react-query 并存，MSW 需在网络层统一拦截。
- **依赖（新增 devDependencies，随本方案审批整体授权）**：`vitest`（与 Vite 6 peer 兼容的稳定线，安装时校验）、`@vitest/coverage-v8`、`jsdom`、`@testing-library/react`、`@testing-library/user-event`、`@testing-library/jest-dom`、`msw@^2`。
- **业务**：遵守提交门禁铁律——完成后每次提交前 `make check` 全绿；`.trae/` 不入库；不放宽既有 E2E/后端断言。
- **Dependencies**：pnpm 安装需访问 npm registry；本机已具备 Node 22 / pnpm 10 与 uv 后端环境（E2E 验证用）。

## Assumptions

- 运行时选 **jsdom**（非 happy-dom）：antd 组件兼容性优先，套件规模小，二者速度差异可忽略。
- 测试文件就近放置（`src/**/*.test.ts(x)`），公共设施放 `src/test/`；E2E 继续留在 `frontend/tests/e2e/`。
- Vitest 配置并入现有 `vite.config.ts`（`vitest/config` 的 defineConfig 向后兼容 Vite 字段），不新增第二份构建配置。
- 覆盖率双门槛通过 v8 全量报告 + 一个轻量校验脚本实现（Vitest 原生 thresholds 仅支持全局/perFile，无法表达"核心 glob 高门槛 + 全局低水位"）。
- E2E 精简后 `make e2e`（webServer 重建隔离库 + seed）仍全部通过，语义不弱化。

## Acceptance Criteria

### AC-1: 单元/组件测试一键可跑且全绿
- **Type**: `rule`
- **Given**: 干净检出的仓库，前端依赖已安装
- **When**: 在 `frontend/` 执行 `pnpm test`
- **Then**: Vitest 发现并运行全部单元与组件测试，全部通过，无需启动后端或浏览器
- **Pass Condition**: `pnpm test`（CI 模式 run 一次）退出码 0
- **Evidence**: 命令输出（用例数、耗时、退出码）

### AC-2: 覆盖率双门槛生效
- **Type**: `rule`
- **Given**: FR-2/FR-3 的测试已就位
- **When**: 执行 `pnpm test:coverage`
- **Then**: 生成 v8 覆盖率报告；核心逻辑集合行覆盖 ≥ 90%、分支 ≥ 85%；全局 src 行覆盖 ≥ 首版校准水位（≥ 30%）；任一不达标命令退出码非 0
- **Pass Condition**: 校验脚本退出码 0，报告中阈值与实际值可见
- **Evidence**: coverage 输出（terminal summary 或 html/json 报告 + 校验结果）

### AC-3: 核心纯逻辑模块全部有测试
- **Type**: `rule`
- **Given**: 测试实现完成
- **When**: 对照 FR-2 模块清单与 FR-3 抽取模块逐一核查
- **Then**: 每个模块存在对应测试文件，且其边界/异常用例（空值、别名、旧格式兼容、缓存、401 等）有断言
- **Pass Condition**: 清单逐模块核对通过，且全部模块纳入 AC-2 高门槛集合
- **Evidence**: 测试文件清单 + 代表性用例代码审查

### AC-4: 四个关键路径组件/集成测试就位且经 MSW
- **Type**: `rule`
- **Given**: 组件测试实现完成
- **When**: 审查 ProtectedRoute、GridCell、ColumnFilterDropdown、视图配置表单四组测试
- **Then**: 均通过统一 render 工具渲染；涉及 API 的场景由 MSW handler 响应；断言聚焦用户可见行为而非内部 state
- **Pass Condition**: 4 组测试存在、通过，且代码中无真实 fetch/axios 网络调用（MSW 未命中请求即失败）
- **Evidence**: 测试代码 + `pnpm test` 输出 + MSW onUnhandledRequest 配置

### AC-5: E2E 下沉精简且链路不弱化
- **Type**: `rule`
- **Given**: 下沉完成
- **When**: 对比变更前后 E2E 套件并执行 `make e2e`
- **Then**: 被移除的 E2E 逻辑断言在单元/组件层存在等价覆盖；端到端链路（登录、行增删改、视图切换、主导航）仍各至少 1 条 E2E；E2E 用例总数 ≤ 26；准入约定写入测试约定
- **Pass Condition**: `make e2e` 全绿；用例计数 ≤ 26；下沉断言映射表可一一对应
- **Evidence**: E2E 运行输出 + 下沉映射说明（记录于任务完成证据）

### AC-6: 提交门禁与 CI 接入
- **Type**: `rule`
- **Given**: 全部测试就位
- **When**: 本地执行 `make check`，并审查 `.github/workflows/ci.yml`
- **Then**: frontend-check 阶段执行 `pnpm test` + 覆盖率校验并通过；CI `frontend-check` job 含对应步骤且为强制门禁；E2E 独立 job 不被合并进 `make check`
- **Pass Condition**: `make check` 退出码 0；CI YAML 含测试步骤且非 continue-on-error
- **Evidence**: `make check` 输出、CI 配置 diff

### AC-7: 测试套件速度
- **Type**: `rubric`
- **Dimension**: 单元+组件全量冷跑耗时（开发机，含 Vitest 启动）
- **Scale**: 1-5
- **Anchors**: 1 = > 45 秒；3 = ≤ 25 秒；5 = ≤ 10 秒
- **Pass Threshold**: >= 4（即 ≤ 15 秒）
- **Evidence**: `pnpm test` 连续 3 次耗时记录（取中位数）

### AC-8: 测试质量与可维护性
- **Type**: `rubric`
- **Dimension**: 用例独立性、AAA 结构、中文描述、行为导向断言、无实现细节耦合、无 flaky 来源、测试数据构造可读性
- **Scale**: 1-5
- **Anchors**: 1 = 大量测内部实现/共享状态/真实等待；3 = 基本可读但存在耦合或重复；5 = 全部行为导向、隔离彻底、设施复用清晰
- **Pass Threshold**: >= 4
- **Evidence**: 独立审查抽查测试代码与设施

### AC-9: 金字塔形态合理
- **Type**: `rubric`
- **Dimension**: 用例数量层级分布（单元 : 组件 : E2E）与"逻辑断言在下层、链路断言在顶层"的契合度
- **Scale**: 1-5
- **Anchors**: 1 = 仍是 E2E 为主或三层倒挂；3 = 有分层但比例失衡；5 = 单元占绝大多数、组件少量精要、E2E 仅核心链路
- **Pass Threshold**: >= 4
- **Evidence**: 三层用例计数统计 + AC-5 下沉映射

### AC-10: 既有质量体系不回归
- **Type**: `rule`
- **Given**: 全部变更完成
- **When**: 执行 lint/typecheck/后端 cov 全套既有门禁
- **Then**: ESLint、tsc、后端 pytest 覆盖率（95%）、`pnpm build`、gitkeep 校验全部保持通过
- **Pass Condition**: 各命令退出码 0
- **Evidence**: `make check` 全量输出（除前端新增测试外的既有阶段）

## Open Questions

- [ ] 全局低水位的具体数值：规则已定为 ≥ 30%，实施首跑后按实际覆盖率校准为 30%~实际值之间的 5 的整数倍，避免门槛失真。
- [ ] FR-3 纯函数抽取的最终清单：实施时逐个判定，与 UI 强耦合、抽取代价大于收益的逻辑不强行抽取，在任务证据中说明取舍。
