# 待办事项跟进机制

本机制规定待办事项从登记到关闭的完整流程，用于承接任务推进中临时产生的协调事项。待办不是备忘清单，而是有责任人、有要求节点的可跟踪工作项。

## 一、登记

1. 任何人在周例会、评审会或日常协作中发现的待跟进事项，均须在 1 个工作日内登记。
2. 登记字段包括编号、类别、事项、创建时间、要求节点、完成日期、责任人与备注。
3. 编号按 TB 加三位序号递增，不得跳号或复用。
4. 「事项」须写成可验证的动作描述，避免「关注一下」这类无法判定完成的表述。
5. 类别取自需求、设计、开发、测试、部署、文档、沟通、运维八类。

示例：TB003 搭建 CI 流水线，创建时间 2026-09-10，要求节点 2026-09-25，责任人王强，备注包含 lint/test/typecheck 三阶段。

## 二、分派

- 登记后由 PMO 在 1 个工作日内指定责任人，未指定的进入「待分派」清单。
- 责任人默认取该事项所属任务的负责人；跨团队事项由 PMO 指定接口人。
- 责任人不明确或需要多人协作时，仍只指定一名主责人。
- 分派结果在按责任人看板中即时可见，避免口头传达。

## 三、要求节点填写规范

| 事项类型 | 节点填写要求 | 示例 |
| --- | --- | --- |
| 评审与确认类 | 不晚于对应里程碑前 3 个工作日 | TB002 评审新版原型，要求节点 2026-09-28 |
| 开发与改造类 | 按估算工期加 2 个工作日缓冲 | TB004 统一 API 返回结构，要求节点 2026-10-10 |
| 测试与验证类 | 不晚于版本提测后 5 个工作日 | TB012 回归测试多租户隔离，要求节点 2026-10-14 |
| 沟通与准备类 | 按会议或启动会实际日期填写 | TB015 启动会准备，要求节点 2026-10-06 |

完成日期在事项关闭时填写，未关闭不得预填；已关闭事项不得回改要求节点。

## 四、催办

1. 要求节点前 2 个工作日，责任人尚未更新进展的，由 PMO 发起一次催办。
2. 超过要求节点仍未完成，事项标记为超期，并升级到周例会通报。
3. 超期 5 个工作日以上，由 PMO 重新评估责任人并可能调整排期。
4. 催办记录写入备注字段，注明催办时间与承诺的新节点。

## 五、关闭

- 责任人完成事项后填写完成日期，并说明产出物存放位置。
- PMO 在按责任人看板中核验，确认产出物可查后方可关闭。
- 关闭后如需重新打开，须新建事项并引用原编号，保持历史可追溯。

## 六、与其他文档的联动

- 由 WBS 任务衍生的待办，须在备注中写明任务ID，便于回溯。
- 因资源冲突产生的待办，须同步登记到《[[资源排期与投入规则]]》的排期变更记录。
- 影响里程碑的待办，须在《[[里程碑与交付计划]]》的交付评审中说明。
- 每周周报中的风险与阻塞章节，直接引用本周新增与超期的待办事项。

> 待办的价值不在于列得多，而在于每条都有唯一责任人和一个能被检验的完成日期。
